## Phase 3 — Data quality checks (rebuilt on Delta Live Tables)

1. ✅ Define and implement checks per Bronze table: schema conformance, null checks on required fields, value-range checks, duplicate-key checks. (Done 2026-11-15 — but as **data quality expectations** rather than hand-rolled check queries: Databricks' first-party pattern for exactly this problem, via Delta Live Tables' `@dlt.expect`/`@dlt.expect_or_fail`. This required rebuilding the ingestion architecture, since DLT can't itself call the Whoop API — see below.)
2. ✅ Run checks as a step in the Databricks Job immediately after ingestion; fail/alert the job (or quarantine bad rows) rather than silently passing bad data downstream. (Done 2026-11-15 — tiered rather than binary: structural checks (`natural_key_present`, `score_state_present`, via `expect_or_fail`) fail the whole pipeline update on any violation, since that can only mean our own fetch step broke, which fails the `dlt_refresh` Job task and triggers Phase 2's retry/email alert. Value-range checks (`recovery_score`/`strain`/`sleep_performance_percentage` in range, via `expect`, log-only) never fail anything, since a single odd value from Whoop isn't fixed by retrying — and each predicate excludes `score_state != 'SCORED'` records so a same-day in-progress cycle never false-positives on its still-null score fields.)
3. ✅ Log check results (pass/fail per check, per run) — this is the "data-quality test pass rate" input for Pipeline Health. (Done 2026-11-15 — DLT's own event log (`event_log(pipeline_id)` SQL table function) tracks `passed_records`/`failed_records` per expectation per flow run automatically; no custom logging table needed for this, unlike Phase 2's `run_metadata` which still covers the fetch step.)

**Architecture rebuild, 2026-11-15**: DLT can't drive the custom OAuth/pagination/rate-limit logic itself (no clean source abstraction for "paginated authenticated REST pull" the way it has for files/Kafka/Delta), so ingestion is now two stages:
- `notebooks/01_whoop_fetch_bronze.py` (replaces `01_whoop_ingest_bronze.py`): unchanged OAuth/pull/backfill/incremental/429-backoff/`run_metadata` logic, but lands raw NDJSON files into a Unity Catalog Volume (`bootcamp_students.bryan_whoop_bronze.landing`) instead of doing `MERGE INTO` itself.
- `pipelines/whoop_dlt_ingestion.py` (new DLT pipeline, id `7d08b214-8dda-480c-9b2f-6205a8496e68`, created via `pipelines/whoop_dlt_ingestion_pipeline.json`): Auto Loader picks up those files into `raw_<endpoint>` Bronze tables, a `<endpoint>_validated` view applies the tiered expectations above, and `dlt.apply_changes` (upsert by `natural_key`, latest-wins by `ingested_at`) lands the final `recovery`/`cycle`/`sleep`/`workout` tables — `apply_changes` specifically because Whoop does revise records after initial scoring (`updated_at` differs from `created_at` on real records), so plain dedup would silently keep an arbitrary version instead of the latest one.
- Modeled directly on the user's own prior DLT pipeline (`trading-ingestion-pipeline`) in this same workspace — same landing-zone-then-Auto-Loader shape, same raw → validated → final layering.
- Verified end-to-end (full backfill + two unattended `jobs run-now` incremental runs): final table counts stayed exactly consistent (recovery 1352, cycle 1396, sleep 1373, workout 1431) with zero structural-check failures, and the value-range checks caught one genuine Whoop data oddity (a `SCORED` workout with a null `strain`) without blocking anything — confirming the tiered design works as intended on real data, not just in theory.

## Phase 4 — Silver layer (cleaned/conformed)

✅ **Done 2026-11-18.** Built as a second library file (`pipelines/whoop_dlt_silver.py`) in the *same* DLT pipeline as `whoop_dlt_ingestion.py` (wired into `pipelines/whoop_dlt_ingestion_pipeline.json`), rather than a separate pipeline/job task — this keeps `dlt.read_stream()` reads of the Bronze tables within one pipeline graph (simple, standard DLT) instead of needing cross-pipeline change-feed reads (more fragile, no benefit here since both layers already run on the same schedule). Tables publish to the `bryan_whoop_silver` schema via a fully-qualified `catalog.schema.table` in each `@dlt.table`'s `name` (multi-schema-per-pipeline, GA since March 2025) but keep an explicit `_silver` suffix (`recovery_silver`, `cycle_silver`, `sleep_silver`, `workout_silver`) because DLT dataset names must be unique pipeline-wide, not just per schema, and Bronze already owns the bare names.

1. ✅ Transform Bronze → Silver: flatten nested JSON fields (via `from_json` against an explicit struct schema per domain, not ad hoc `get_json_object` calls), cast types, standardize timestamps to UTC (`timezone_offset` kept as its own column for later local-time derivation), rename fields for clarity (`id` → `cycle_id`/`sleep_id`/`workout_id`, `start`/`end` → domain-prefixed). First deploy (2026-11-18) went through three rounds of fixes against real payloads before landing clean:
   - `schema=` on `@dlt.table` is not a target-schema override (it's a DDL column-definition string); routing a table to a non-default schema within one pipeline needs a fully-qualified `catalog.schema.table` in `name` instead.
   - WHOOP's `id` is a UUID string for `sleep`/`workout` but a plain integer for `cycle` — had typed all three as `Long`, which silently nulled `sleep_id`/`workout_id` (and `recovery_silver.sleep_id`, not caught by any expectation there) via `from_json`'s permissive-mode behavior rather than erroring.
   - Workout's zone breakdown key is `zone_durations` (plural), not `zone_duration` — also silently all-NULL, not caught by any expectation.
   - Added `sleep_silver.cycle_id` (FK, present in the real payload but missed originally) and `workout_silver.sport_name` (more legible than the numeric `sport_id`).
   - A type change on an already-materialized column (`sleep_id`/`workout_id` Long → String) isn't an additive schema change Delta will auto-merge — needed an explicit full-refresh of the whole pipeline (`databricks pipelines start-update --full-refresh`) to land cleanly, since the first failed attempts had already partially committed the wrong types to `sleep_silver`, `workout_silver`, and `recovery_silver`'s backing tables.
   - Verified 2026-11-18 via the SQL Statement Execution API: sample rows from all four Silver tables confirmed every column populated as expected (including the previously-unverified rest of `RECOVERY_SCHEMA`/`CYCLE_SCHEMA`) — `distance_meter`/`altitude_gain_meter`/`altitude_change_meter` are genuinely null on the sampled workouts (jiu-jitsu, surfing — no GPS), not a bug.
2. ✅ Conform grain per domain — this fell out of Bronze's existing natural-key dedup rather than needing new logic: recovery and cycle are already one row per cycle, sleep and workout one row per session. Sleep's `nap` field is surfaced as `is_nap` so Gold-layer day-level metrics can exclude naps explicitly instead of this layer silently dropping or merging them.
3. ✅ Re-run the Phase 3 quality checks against Silver: same tiered pattern (`expect_or_fail` on key/`score_state` presence, log-only `expect` on score ranges), now against the flattened/typed columns rather than Bronze's `get_json_object` extracts — caught the three real bugs above during development, confirming the tiered design catches Silver-layer bugs too, not just Bronze's.

**Post-deploy production incident (2026-11-19):** the unattended daily job's `dlt_refresh` task failed fatally — `recovery_silver` hit `DELTA_SOURCE_TABLE_IGNORE_CHANGES` ("Streaming tables may only use append-only streaming sources... detected a data update... Operation: MERGE... Source table name: bootcamp_students.bryan_whoop_bronze.recovery"). Root cause: `_flatten()` read Bronze via `dlt.read_stream()`, but Bronze tables are `dlt.apply_changes` targets that receive `MERGE` writes whenever Whoop revises an already-scored record (the exact behavior `apply_changes` was built for in Phase 3) — a streaming read can't tolerate that, and it only surfaces the first time a real update (not just an insert) lands, which is why this didn't show up until now, a day after first deploy. Databricks' own suggested escape hatch, `skipChangeCommits=true`, was rejected: it would silently drop revised records going forward, reintroducing the exact staleness problem `apply_changes` exists to prevent. Fixed by switching all four Silver tables to `dlt.read()` (batch), making them materialized views that recompute each run instead of tailing an append-only log — the same pattern Gold already uses to read Silver, for the same reason. Fix committed (`084178e`).

**Second incident, same day (2026-11-20):** the `084178e` fix was correct but didn't actually take effect in production. Changing a DLT table's declared kind (`STREAMING_TABLE` → `MATERIALIZED_VIEW`, which is what switching to `dlt.read()` requires) needs the existing table dropped first — `databricks pipelines start-update --full-refresh` only resets table *data*, it does not change a table's kind. The 2026-11-19 full-refresh deploy that this doc previously described as "clean, zero error events" had in fact failed the same `CANNOT_CHANGE_DATASET_TYPE` way (confirmed from the pipeline event log, update `6b843b07…`), so all four `*_silver` tables stayed `STREAMING_TABLE`, and every subsequent unattended run kept failing/auto-retrying on whichever table DLT checked first (`recovery_silver`, later `workout_silver` — the table named in the error is incidental, not the actual fault). Fixed by dropping all four `*_silver` tables plus the orphaned `__materialization_mat_...` staging tables DLT leaves behind on a failed materialization, then re-running `--full-refresh`. Verified via `information_schema.tables` (all four now `MATERIALIZED_VIEW`), via row counts matching the expected +5/day drift with no data loss, and via a full `jobs run-now` of `468100317206602` succeeding end-to-end on the normal incremental path, not just full-refresh. **Lesson:** a full-refresh update being clean does not confirm a dataset-type change took effect — check the table's actual kind in `information_schema.tables` (or the pipeline UI) after this kind of fix, not just the update's error count.

## Phase 5 — Gold layer (derived metrics)

✅ **Done 2026-11-18.** Built as a third library file (`pipelines/whoop_dlt_gold.py`) in the same DLT pipeline as Bronze/Silver (wired into `pipelines/whoop_dlt_ingestion_pipeline.json`), publishing to `bootcamp_students.bryan_whoop_gold` via a fully-qualified `name` per table, same pattern Phase 4 settled on. Reads Silver via `dlt.read` (batch, not streaming) since every metric here is a trailing-window calculation over the full history — small enough (~1500 rows/table) that recomputing from scratch each run is simpler than incremental window-function state. All rolling windows use a calendar-day index (`datediff` from a fixed epoch) with `rangeBetween`, not row position (`rowsBetween`), so a missed-wear gap day doesn't silently shrink a "7-day" window to fewer actual days.

First deploy caught two real bugs, both self-inflicted (not Databricks quirks like Phase 4's): `strain_next_day_recovery_gold` called `.select(...)` (which drops the `day_index` helper column) *before* the `.withColumn(...)` that needed `day_index` as a window `orderBy` column — `AnalysisException: UNRESOLVED_COLUMN`, failing pipeline update initialization. Fixed by reordering: apply the window first, select the clean output columns last. Found by inspection while fixing that one: `recovery_same_day_strain_gold` had the opposite problem — it never selected `day_index` away at all, so it would have silently leaked that internal column into the published Gold table. Both fixed in the same pass before redeploying.

1. ✅ **ACWR** — 7-day rolling average / 28-day rolling average of daily Strain score, per day. Table: `cycle_acwr_gold` (`cycle_id`, `cycle_date`, `strain`, `acute_load_7d`, `chronic_load_28d`, `acwr`).
2. ✅ **Personal rolling-percentile baseline** — Recovery score, HRV, and RHR each as a percentile rank against their own trailing 60-day window (`size(filter(window_values, x -> x <= today)) / size(window_values) * 100`, since Spark has no built-in trailing-window percentile-rank function). Table: `recovery_baseline_gold`. Note for Phase 6's caption logic: lower RHR is physiologically better, so a high `rhr_percentile_60d` means "higher than usual," not "healthier" — needs different phrasing than the recovery/HRV percentiles, which both read "higher is better."
3. ✅ **Lagged correlation** — two tables, each a rolling 90-day Pearson correlation (`F.corr(...).over(window)`) plus the underlying paired data for a scatter chart: `strain_next_day_recovery_gold` (Strain(day N) vs Recovery(day N+1), joined via `date_sub(cycle_date, 1)` on the recovery side) and `recovery_same_day_strain_gold` (Recovery(day N) vs same-day Strain(day N)).
4. ✅ **Recovery momentum** — 7-day MA vs 28-day MA of Recovery score, plus a derived state (`rising`/`declining`/`flat`) from comparing the two with a small flat-band tolerance (±2 points) rather than exact equality. Table: `recovery_momentum_gold`.
5. ✅ Validated each derived metric via the SQL Statement Execution API (2026-11-18), both for structural correctness and physiological plausibility: ACWR hand-checked for 2026-11-18 (9.7295/12.08 = 0.8054, matches stored value exactly); Strain→next-day-Recovery correlation came back consistently negative (~−0.41 to −0.43, strain predicts a next-day recovery *drop*, matching CLAUDE.md's own example caption's magnitude); same-day Recovery↔Strain correlation came back near zero (recovery is capacity, not realized same-day strain); a 100th-percentile RHR row lined up with that period's worst recovery score — all directionally sane, not just error-free.
